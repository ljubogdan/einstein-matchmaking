# Keeping peak-hour query response within SLA as transaction volumes grow

**Company:** Voltis Pay d.o.o. [C143], Fintech, 47 employees, Novi Sad.  
**Researcher:** Strahinja Radović, Research Associate, Faculty of Technical Sciences, Department of Computing and Control Engineering [R0385].  
**Format:** Contract research  
**Supervisors / contacts:** Department of Computing and Control Engineering liaison (academic) and CTO (company)

### The problem
- The cluster processes roughly 180,000 transactions a day but misses the 200 ms SLA during evening peaks. [C143-CH2]
- During peak hours the cluster records latency of 320 to 450 ms, with the most expensive operations being complex JOIN queries joining transactions, user profiles, and partner configuration tables. [C143-CH2]
- The company must either rearchitect the data layer or find a smarter query routing strategy before scaling to 500,000 transactions. [C143-CH2]

### Work packages
1. Which query routing strategy most effectively distributes JOIN-heavy workloads across replica nodes during evening peak hours while sustaining SLA compliance?
2. What partitioning scheme keeps OLTP tail latency within SLA bounds as daily transaction volume grows toward the target?
3. How does load forecasting based on observed queue lengths improve scheduling decisions under bursty evening traffic?
4. Can read redistribution to replica nodes resolve peak-hour SLA breaches without requiring a full rearchitecture of the data layer?

### Plan
| Phase | Work | Result |
|---|---|---|
| Diagnosis | Analyse query traces, Grafana metrics, and workload logs to characterise the evening traffic pattern, identify the root causes of JOIN-heavy query latency, and map which nodes absorb peak load. | Bottleneck diagnosis report covering root causes and candidate intervention points, delivered at month 1. |
| Strategy Design and Sandbox Prototype | Design candidate query routing strategies, partitioning schemes, and load-forecasting approaches — including read redistribution to replica nodes — and implement them in the sandbox environment with iterative feedback from the engineering team. | Prototype query routing and partitioning strategy validated against sandbox workloads, delivered at month 3. |
| Load Testing at Target Volume | Simulate the target transaction volume against each candidate strategy, measure SLA compliance and tail latency, and select the configuration that avoids a full rearchitecture while meeting peak-hour requirements. | Load-test results demonstrating per-strategy SLA compliance at the simulated target volume, delivered at month 5. |
| Recommendations and Handover | Compile final recommendations into a report, document implementation steps, and conduct a handover session covering configuration changes and monitoring thresholds for the engineering team. | Final recommendations report and handover documentation delivered to the engineering team at month 6. |
