# Cutting false bans to restore player trust

**Company:** VoxelRealm a.d. [C115], Game development, 120 employees, Novi Sad.  
**Researcher:** Dragana Tadić, Assistant Professor, Faculty of Technical Sciences, Department of Computing and Control Engineering [R0856].  
**Format:** Contract research  
**Supervisors / contacts:** Assistant Professor, Department of Computing and Control Engineering (academic) and Head of Backend Engineering (company)

### The problem
- The anti-cheat system flags about 900 accounts a day but the review team can only process 200, leaving legitimate players getting banned. [C115-CH1]
- Daily active users fell by 7% in the last quarter, a drop the company attributes partly to trust issues. [C115-CH1]
- Every reduction of false positives in BehaviorWatch causes more actual cheating cases to go undetected. [C115-CH1]

### Work packages
1. Which semi-supervised and one-class detection methods produce the lowest false-positive rate when applied to the available player event log data?
2. What per-account explanation outputs allow moderators to act on flagged cases more quickly within the existing review workflow?
3. How do player behaviour distributions shift following game patches, and what trigger conditions should prompt model retraining?
4. How does the new detection pipeline compare to the current threshold logic when evaluated on held-out labelled data?

### Plan
| Phase | Work | Result |
|---|---|---|
| Data audit and baseline | Audit the player event dataset, document its structure and label coverage, and measure the current false-positive rate of the existing threshold system. | A confirmed project plan, a baseline false-positive figure, and a prepared dataset ready for model training. |
| Prototype model development | Design and train semi-supervised and one-class anomaly detection models on the prepared dataset, then evaluate them on a held-out split to address the first and fourth research questions. | A prototype detection pipeline with measured false-positive and detection performance, delivered for company review. |
| Explainability integration and workflow test | Add a per-account explainability layer to the prototype and test it within the moderator review workflow, addressing the second research question. | An integrated pipeline with explainable decision outputs and a tested moderator workflow. |
| Drift monitoring and final delivery | Implement a concept drift monitoring protocol and retraining recommendations, conduct final evaluation on held-out data, and complete all documentation, addressing the third research question. | Final detection model, performance documentation, and a retraining protocol, all delivered to the company. |
