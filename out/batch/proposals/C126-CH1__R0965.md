# Automated LiDAR pipeline for classified delivery within 48 hours of each city flight

**Company:** Geodata Pro d.o.o. [C126], Geospatial / GIS services, 34 employees, Novi Sad.  
**Researcher:** Anja Bošković, Research Associate, Faculty of Technical Sciences, Department of Civil Engineering and Geodesy [R0965].  
**Format:** Contract research  
**Supervisors / contacts:** Research Associate (project lead, processing design) (academic) and Technical Director (pipeline integration and milestone sign-off) (company)

### The problem
- A single city-block survey runs to 80 GB, and clients want classified, feature-extracted outputs delivered within 48 hours of the flight. [C126-CH1]
- A full urban dataset takes between five and seven days end-to-end on a local processing cluster with twelve workstations, and manual job-splitting generates coordination overhead that eats up the time saved. [C126-CH1]
- The per-job cost of a commercial cloud processing platform at the company's survey volumes would exceed what most municipal contracts allow, and the stated target is consistent 36-to-48-hour turnaround on datasets up to 120 GB without adding permanent hardware cost. [C126-CH1]

### Work packages
1. What tile size and overlap parameters minimise boundary artefacts and inter-GPU communication overhead when partitioning large urban LiDAR datasets for parallel processing on a GPU cluster?
2. Which ML-based classification architecture achieves the best balance between classification accuracy and inference throughput for urban feature extraction within the required delivery window?
3. How can existing LAStools and PDAL processing steps be integrated into a tile-parallel GPU workflow while remaining compatible with the company's on-premises workstation cluster?
4. Under what dataset-size and survey-volume conditions can burst cloud compute supplement on-premises processing while remaining within municipal contract budget constraints?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 – Tile partitioning and ML architecture selection (M1–M3) | Tile partitioning parameters and ML classification architectures are evaluated on the Faculty GPU cluster using representative urban datasets, covering tile overlap width, boundary handling strategies, and throughput at target dataset sizes. | Prototype pipeline processing a single 80 GB block within 48 hours on the Faculty GPU cluster, with a benchmark report documenting throughput, classification accuracy, and artefact handling. |
| Phase 2 – LAStools and PDAL integration and multi-dataset validation (M4–M6) | The prototype pipeline is adapted to incorporate existing LAStools and PDAL processing steps and deployed on the company's on-premises cluster, then verified on three real urban datasets to confirm outputs meet client delivery specifications. | Pipeline operating on the company's local cluster, verified against three real urban datasets, with integration notes documenting cluster configuration. |
| Phase 3 – Scaling, cloud model evaluation, and documentation (M7–M9) | Pipeline performance is tested at the upper dataset-size target, conditions for viable burst cloud compute within municipal contract budgets are examined, and final pipeline code, integration guide, and acceptance test are prepared. | Documented pipeline code, integration guide, and acceptance test results on a 120 GB dataset delivered to the company. |
