# Unsupervised Anomaly Detection for OT Networks Deployable on Edge Sensors

**Company:** SecureEdge Labs [C032], Cybersecurity, 19 employees, NTP Novi Sad.  
**Faculty:** Faculty of Technical Sciences, Department of Computing and Control Engineering [R1015].  
**Format:** Joint project  
**Supervisors / contacts:** Principal Investigator (research delivery and student supervision) (academic) and SecureEdge Labs Technical Lead (milestone sign-off and data access approvals) (company)

### The problem
- Detecting intrusions on Modbus and BACnet networks is impractical with hand-written rules because slow, low-volume probing goes entirely undetected. [C032-CH1]
- Statistical baselining drifts with shift patterns and seasonal production changes, generating noise that analysts cannot keep up with. [C032-CH1]
- Because real incidents are rare, customers prohibit attack simulations, and public datasets are thin, the company needs to build detection models from unlabelled traffic. [C032-CH1]

### Work packages
1. Can autoencoder-based models trained on unlabelled Modbus and BACnet traffic generalise across three operationally distinct customer sites?
2. What window size and encoding granularity optimise detection sensitivity while keeping inference within 512 MB RAM on an ARM core?
3. How should models be updated when production baselines drift due to seasonal or shift-pattern changes, without reintroducing false-positive noise?
4. Can a federated or incremental training strategy allow models from multiple sites to improve collectively without sharing raw packet logs?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 — Data preparation and baseline model (M1–M3) | Ingest and anonymise eighteen months of packet logs from three sites; define feature representations for Modbus and BACnet sessions; train an initial autoencoder on benign traffic and measure reconstruction-error thresholds. | Baseline autoencoder model with documented false-positive rate on held-out site data. |
| Phase 2 — Edge optimisation and hardware validation (M4–M6) | Apply model compression, quantisation, and pruning techniques to fit inference within sensor constraints; deploy candidate model on EdgeWatch hardware and profile RAM and latency under realistic traffic loads. | Edge-feasible model variant validated on EdgeWatch sensor hardware. |
| Phase 3 — BACnet extension and comparative evaluation (M7–M9) | Extend feature engineering and model architecture to cover BACnet protocol semantics; run comparative evaluation of detection architectures against documented attack scenarios on both protocols. | BACnet-capable model with comparative evaluation report covering detection accuracy and resource consumption. |
| Phase 4 — Integration and delivery (M10–M12) | Package deployable model artefacts, write integration documentation for the EdgeWatch firmware pipeline, and conduct end-to-end testing with the SOC analyst workflow. | Deployable model package with integration documentation ready for production rollout. |
