# Edge-deployable anomaly detection for unlabelled OT network traffic

**Company:** SecureEdge Labs [C032], Cybersecurity, 19 employees, NTP Novi Sad.  
**Faculty:** Faculty of Technical Sciences, Department of Computing and Control Engineering [R1015].  
**Format:** Joint project  
**Supervisors / contacts:** Principal Investigator (research delivery and student supervision) (academic) and SecureEdge Labs Engineering Lead (milestone sign-off and data access approvals) (company)

### The problem
- Hand-written rules miss slow, low-volume probing entirely. [C032-CH1]
- Any detection model must run inference on an edge sensor with constrained resources, making large deep-learning architectures impractical without explicit optimisation for the target hardware. [C032-CH1]

### Work packages
1. Can autoencoder-based models trained only on benign OT traffic reliably flag anomalous sequences across Modbus and BACnet simultaneously?
2. What windowing and encoding granularity choices allow an anomaly detection model to fit within the memory and compute budget of an ARM edge device?
3. How should detection thresholds be tuned to remain stable as production patterns shift across seasons and operating shifts?
4. Can a federated training scheme across multiple customer sites improve model generalisation without exposing raw customer traffic?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 — Data preparation and baseline architecture (M1–M3) | Define anonymisation pipeline for packet logs; analyse traffic structure and session patterns across three sites; agree on feature encoding and window size; train and evaluate candidate autoencoder architectures on anonymised logs. | Baseline model architecture agreed and validated on anonymised logs (Milestone M3). |
| Phase 2 — Edge optimisation and prototype (M4–M6) | Apply model compression, quantisation, and pruning to meet the RAM and compute constraints of the ARM target; implement edge inference code in the existing Rust processing pipeline; verify latency and memory footprint on sensor hardware. | Edge-feasible model prototype running on ARM target hardware (Milestone M6). |
| Phase 3 — Threshold tuning and field validation (M7–M9) | Deploy prototype at one customer site; collect false-positive and detection feedback from SOC analysts; iteratively tune decision thresholds to handle concept drift from shift and seasonal patterns without retraining from scratch. | Low-false-positive threshold configuration validated in a live OT environment (Milestone M9). |
| Phase 4 — Final artefacts and reporting (M10–M12) | Harden model artefacts for production deployment; complete integration testing across all three sites; write validation report covering detection performance, resource consumption, and operational constraints; prepare publication draft for company review. | Deployable model artefacts, edge integration code, and validation report delivered (Milestone M12). |
