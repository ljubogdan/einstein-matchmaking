# Catching unusual OT network behaviour without attack examples

**Company:** SecureEdge Labs [C032], Cybersecurity, 19 employees, NTP Novi Sad.  
**Researcher:** Vuk Đukić, Associate Professor, Faculty of Technical Sciences, Department of Computing and Control Engineering [R1015].  
**Format:** Joint project  
**Supervisors / contacts:** Associate Professor (research lead) (academic) and Technical Project Lead (security engineering) (company)  

### The problem
- The company has almost no labelled examples of actual attacks on Modbus and BACnet networks because real incidents are rare and customers do not allow attack simulations on live plant. [C032-CH1]
- Hand-written rules miss slow, low-volume probing, and statistical baselines drift with shift patterns and seasonal production changes, generating noise analysts cannot keep up with. [C032-CH1]
- Any detection model must run inference on the edge sensor, which has 512 MB of RAM and a modest ARM core, and must be deployable within twelve months. [C032-CH1]

### Work packages
1. Can an autoencoder trained only on unlabelled Modbus and BACnet traffic flag anomalous sequences, measured against scripted fault injections on the company's test bench and a held-out set of labelled attack traces from a published OT testbed dataset?
2. What concept-drift adaptation mechanism keeps false-positive rates stable across seasonal production changes, measured against analyst-labelled noise events from the eighteen months of site logs?
3. Can the trained model be compressed to run inference within 512 MB RAM on the ARM target while achieving a detection rate of at least 90% on the scripted fault set and the held-out labelled attack traces?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 – Months 1–3: data preparation and baseline model | University designs autoencoder architecture for Modbus and BACnet sequences; company provides anonymised packet logs and runs preprocessing with its in-house parsers; university sources a published OT testbed dataset with labelled attack traces for held-out evaluation. | Baseline autoencoder model trained on anonymised logs, with detection rate benchmarked against scripted fault injections on the company test bench and against the held-out labelled attack traces from the published dataset. |
| Phase 2 – Months 4–6: concept-drift adaptation | University develops and trains a drift-adaptation mechanism using held-out log segments spanning shift and seasonal changes; company security engineers label a reference set of noise events from the eighteen months of site logs for validation. | Drift-adapted model validated on held-out log segments, with false-positive rate measured against the analyst-labelled noise reference set. |
| Phase 3 – Months 7–9: edge compression and profiling | University applies model compression and quantisation; company profiles RAM and latency on the ARM target using EdgeWatch sensor hardware listed in the term sheet. | Compressed inference module profiled within 512 MB RAM on the ARM target, achieving at least 90% detection rate on the scripted fault set and the held-out labelled attack traces. |
| Phase 4 – Months 10–12: integration and replay validation | Company security engineers integrate the inference module into EdgeWatch sensor firmware; company replays held-out historical anonymised logs through the deployed sensor on the test bench; university analyses resulting detections. | Inference module running inside EdgeWatch sensor with a field-validation report based on replay of held-out historical logs, delivered to both parties. |
