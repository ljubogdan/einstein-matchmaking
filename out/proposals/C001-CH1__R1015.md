# Site-specific unsupervised anomaly detection for Modbus TCP and BACnet/IP embedded in ProtoSense firmware

**Company:** ArmaturaSec d.o.o. [C001], Cybersecurity, 67 employees, Zrenjanin.  
**Faculty:** Faculty of Technical Sciences, Department of Computing and Control Engineering [R1015].  
**Format:** Joint project  
**Supervisors / contacts:** Associate Professor, Department of Computing and Control Engineering (academic) and CTO / Head of Product Engineering (company)

### The problem
- No client has ever supplied a packet capture containing a confirmed attack, so there is no labeled malicious data to train a supervised classifier on. [C001-CH1]
- A supervised classifier trained on public ICS datasets produced so many false positives that clients disabled the alerts entirely. [C001-CH1]
- The required solution must learn what normal behaviour looks like for a specific site and raise a flag only when behaviour drifts from that learned baseline. [C001-CH1]

### Work packages
1. Can an autoencoder trained solely on site-specific Modbus TCP and BACnet/IP traffic sustain a false-positive rate low enough for continuous unattended operation across diverse industrial sites?
2. What model architecture and compression strategy allows real-time anomaly scoring within the memory and compute budget of the target embedded security processor?
3. How should the baseline model adapt incrementally as legitimate operational behaviour evolves over time without triggering spurious alerts?
4. Does a single detection pipeline generalise across both Modbus TCP and BACnet/IP protocol families, or does each protocol require a separately trained model?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 — Traffic Analysis and Algorithm Design (M1–M6) | Characterise the structure and variability of archived Modbus TCP and BACnet/IP captures; design and train an unsupervised anomaly detection model on site-specific normal traffic; evaluate reconstruction-error thresholding strategies. | Baseline algorithm prototype validated on held-out archived traffic with documented detection and false-positive rates. |
| Phase 2 — Model Compression and On-Device Porting (M7–M12) | Apply quantisation, pruning, and knowledge distillation to reduce model footprint; port the compressed model to the embedded hardware platform; measure inference latency and RAM usage under realistic packet forwarding load. | On-device implementation with a latency and resource benchmark report confirming feasibility on the target hardware. |
| Phase 3 — Firmware Integration and End-to-End Testing (M13–M18) | Integrate the on-device model into the ProtoSense firmware codebase; conduct end-to-end testing on the hardware bench using archived traffic and protocol simulators; refine alert explanation logic for non-technical operators. | Integrated ProtoSense firmware release candidate ready for client pilot deployment. |
