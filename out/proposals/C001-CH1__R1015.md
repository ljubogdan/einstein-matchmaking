# Catching abnormal traffic on industrial networks without attack examples

**Company:** ArmaturaSec d.o.o. [C001], Cybersecurity, 67 employees, Zrenjanin.  
**Researcher:** Vuk Đukić, Associate Professor, Faculty of Technical Sciences, Department of Computing and Control Engineering [R1015].  
**Format:** Joint project  
**Supervisors / contacts:** Principal investigator (academic) and ArmaturaSec engineering lead (company)  

### The problem
- The ProtoSense module must flag abnormal Modbus and BACnet behaviour, but no client has ever provided a packet capture containing a confirmed attack. [C001-CH1]
- A supervised classifier trained on public ICS datasets produced so many false positives in real deployments that clients started switching the alerts off. [C001-CH1]
- The company needs a method that learns what normal looks like on a specific site and raises a flag when behaviour drifts from that baseline. [C001-CH1]

### Work packages
1. Can an autoencoder trained on site-specific Modbus TCP captures detect injected function-code anomalies, measured against company engineer consensus labels on scripted faults produced during Phase 2 bench work?
2. Can the same unsupervised baseline approach extend to BACnet/IP traffic, measured against scripted fault scenarios executed on the company's hardware-in-the-loop bench with physical PLC simulators?
3. What traffic window size and encoding granularity minimise false positives on multi-site archives, measured against detection rate on the labelled fault set assembled in Phase 1 bench runs?
4. Can the trained model produce an explanation of each flagged deviation that a plant manager can act on, measured against a structured readability rubric applied by three domain practitioners?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 — Baseline modelling and initial fault validation (months 1–6) | University leads autoencoder design and training on normal-traffic archives; company engineers script an initial fault set on the hardware-in-the-loop bench with physical PLC simulators and run those faults against the trained model. | A trained baseline model and a validation report covering reconstruction-error distributions on normal traffic and detection rate on the initial scripted fault set. |
| Phase 2 — Full bench integration and consensus labelling (months 7–12) | Company engineers integrate the model into ProtoSense firmware and extend fault scenarios to cover BACnet/IP; company engineers produce consensus labels for all scripted faults; university evaluates detection rate against those labels. | A prototype running on the hardware bench, a labelled fault dataset, and a benchmark report covering detection rate per fault category and forwarding latency. |
| Phase 3 — False-positive and explainability study (months 13–15) | University analyses false-positive rate across multi-site archive replays using the labelled fault set as ground truth and designs a plain-language explanation layer; company engineers validate outputs in operator feedback sessions. | A false-positive rate and explainability report with per-site tuning recommendations, delivered to both parties. |
| Phase 4 — Deployable component and final report (months 16–18) | Company engineers package the validated method as a deployable firmware component for ProtoSense; university produces the final technical report and prepares a journal submission. | A deployable firmware component, a final technical report, and a submitted journal paper. |
