# Deployable Anomaly Detection for Modbus and BACnet Networks Without Labelled Attack Data

**Company:** ArmaturaSec d.o.o. [C001], Cybersecurity, 67 employees, Zrenjanin.  
**Faculty:** Faculty of Technical Sciences, Department of Computing and Control Engineering [R1008].  
**Format:** Joint project  
**Supervisors / contacts:** Full Professor, Department of Computing and Control Engineering (academic) and ArmaturaSec lead engineer (ProtoSense module owner) (company)

### The problem
- None of the clients has ever provided a packet capture that contains a confirmed attack, leaving the ProtoSense module with no labelled malicious traffic on which to train a classifier. [C001-CH1]
- A supervised classifier fed on public ICS datasets flagged so many false positives in real deployments that clients started switching the alerts off, making the approach unfit for production. [C001-CH1]
- The required approach must learn what normal looks like on a specific site and raises a flag when behaviour drifts from that baseline. [C001-CH1]

### Work packages
1. Which unsupervised baseline modelling algorithm best captures site-specific normality in Modbus TCP and BACnet/IP traffic while fitting within the computational budget of an embedded OT appliance?
2. What packet-level and session-level features of Modbus TCP and BACnet/IP traffic produce the most discriminative statistical profiles with the lowest false positive rates on operational captures?
3. How should a recalibration mechanism be designed to adapt baselines to legitimate operational changes without masking gradual or slow-drift intrusion patterns?
4. How can anomaly alerts be structured so that a plant operator without cybersecurity expertise can interpret and act on them?

### Plan
| Phase | Work | Result |
|---|---|---|
| Feature engineering and data preparation (M1–M3) | Analyse the traffic archives to identify the most informative packet-level and session-level features for Modbus TCP and BACnet/IP; establish a data pipeline compatible with the ProtoSense firmware. | A documented feature set and cleaned dataset partition ready for algorithm evaluation. |
| Algorithm selection and baseline prototyping (M4–M6) | Implement and compare candidate unsupervised methods on the archived captures using the prepared features; select the approach with the best detection-to-false-alarm trade-off on real operational data. | M6 milestone: baseline modelling method selected and prototyped on traffic archives. |
| Embedded integration and test-build validation (M7–M12) | Port the selected detector to the embedded Linux target, optimise for inference latency, and integrate into a ProtoSense test build validated on the hardware bench with PLC simulators. | M12 milestone: embedded-deployable detector integrated into ProtoSense test build. |
| Field validation and final reporting (M13–M18) | Deploy the detector on client sites under a monitored trial, collect field performance data, refine detection thresholds, and document findings in the final project report. | M18 milestone: field-validated detector and final report ready for publication review. |
