# Site-Specific Anomaly Detection for Modbus and BACnet Networks on Embedded Hardware

**Company:** ArmaturaSec d.o.o. [C001], Cybersecurity, 67 employees, Zrenjanin.  
**Faculty:** Faculty of Technical Sciences, Department of Computing and Control Engineering [R1008].  
**Format:** Joint project  
**Supervisors / contacts:** Principal Investigator (Full Professor) responsible for research deliverables and student supervision (academic) and Designated technical lead engineer (ArmaturaSec) responsible for milestone sign-off and NDA compliance (company)

### The problem
- Detecting threats on operational technology networks is blocked by a total absence of labelled attack traffic, making supervised classifiers unusable in real deployments. [C001-CH1]
- A prior attempt using public ICS datasets produced so many false positives that clients disabled the alerts, confirming that generic training data cannot substitute for site-specific baselines. [C001-CH1]
- The required solution must learn normal behaviour per site from unlabelled traffic and run inference on-device. [C001-CH1]

### Work packages
1. Which unsupervised baseline modelling algorithms — kernel density estimation, one-class SVM, or lightweight autoencoders — best capture site-specific Modbus TCP and BACnet/IP normality across diverse operational environments?
2. What feature sets derived from inter-request intervals, function code sequences, and payload value distributions provide stable, low-drift baselines under normal seasonal and load variation?
3. Can sliding-window recalibration strategies maintain detection accuracy on embedded hardware within the latency and memory constraints of the ProtoSense platform?
4. How should detection thresholds and alert explanations be presented so that a plant manager can understand and act on an anomaly flag without security expertise?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 — Baseline Algorithm Selection (M1–M6) | Evaluate candidate unsupervised algorithms against archived Modbus TCP and BACnet/IP captures; characterise feature stability across sites; select and validate the baseline modelling approach on archived traffic under NDA. | Algorithm selection report and validated baseline model with false-positive and detection-rate metrics on real site data, meeting M6 milestone. |
| Phase 2 — Embedded Prototype (M7–M12) | Port the selected algorithm to the ProtoSense firmware on the NetGuard-OT hardware bench; measure packet forwarding latency impact; tune recalibration schedules and memory footprint for embedded constraints; run hardware-in-the-loop tests with PLC simulators. | Embedded prototype running on ProtoSense hardware with documented latency benchmarks, meeting M12 milestone. |
| Phase 3 — Integration and Evaluation (M13–M18) | Integrate the anomaly detection module into the ProtoSense firmware codebase; conduct full evaluation including edge-case injection on the ICS testbed; prepare operator-facing alert explanations; complete IP documentation for transfer. | Production-ready integrated module with evaluation report and all IP artefacts transferred per term sheet, meeting M18 milestone. |
