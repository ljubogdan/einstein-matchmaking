# Finding network anomalies on industrial sites without prior attack examples

**Company:** ArmaturaSec d.o.o. [C001], Cybersecurity, 67 employees, Zrenjanin.  
**Researcher:** Krisztina Kiss, Full Professor, Faculty of Technical Sciences, Department of Computing and Control Engineering [R1008].  
**Format:** Joint project  
**Supervisors / contacts:** Full Professor, Department of Computing and Control Engineering, Faculty of Technical Sciences (academic) and Lead Engineer, ProtoSense (company)

### The problem
- The ProtoSense module monitors Modbus and BACnet networks at sites where none of the clients has ever provided a packet capture that contains a confirmed attack, because a few of them have been running their networks for twenty years with no security monitoring at all. [C001-CH1]
- A supervised classifier trained on public ICS datasets flagged so many false positives in real deployments that clients started switching the alerts off. [C001-CH1]
- What is needed is a method that learns what normal looks like on a specific site and raises a flag when behaviour drifts from that baseline, with no attack examples required. [C001-CH1]

### Work packages
1. Which unsupervised and one-class methods achieve the lowest false-positive rate when trained solely on unlabelled Modbus TCP and BACnet/IP captures from a single operational site?
2. What feature representations of Modbus TCP and BACnet/IP traffic allow accurate baseline modelling while remaining feasible for inference on constrained embedded hardware?
3. How should a site-specific statistical baseline be recalibrated over time to track normal operational drift without human intervention?
4. What deployment configuration allows the anomaly detector to run within the ProtoSense firmware without affecting packet forwarding latency?

### Plan
| Phase | Work | Result |
|---|---|---|
| Phase 1 (months 1–6): Baseline modelling selection and validation | Characterise statistical properties of the company's Modbus TCP and BACnet/IP traffic archives; implement and compare candidate unsupervised and one-class methods on site-specific unlabelled data; select the approach that minimises false-positive rate and suits the embedded target. | A baseline modelling approach selected and validated on the company traffic archives, with a documented comparison of candidate methods and feature representations addressing the first two research questions. |
| Phase 2 (months 7–12): Prototype integration and hardware bench testing | Integrate the selected detector into the ProtoSense firmware; run hardware-in-the-loop tests with the company's physical PLC simulators; iterate on computational footprint and latency to meet embedded constraints; address the deployment configuration research question. | A prototype anomaly detector integrated into ProtoSense firmware and tested on the hardware bench, with latency and resource measurements recorded. |
| Phase 3 (months 13–18): Evaluation and deployment guidance | Conduct final evaluation across multiple site profiles using both the company's traffic archives and the university's ICS testbed; develop and document recalibration procedures that address baseline drift without human intervention; produce deployment architecture documentation. | A final evaluation report with calibration guidance and deployment architecture recommendations, together with an integrated prototype suitable for the ProtoSense module. |
